# T94 · GUI 端到端验证（作业提交 → 结果回传 → 虚拟机自动关闭）

- 阶段：E1（求解链路闭环）
- 依赖：T29（求解链路本身）、T34（求解入口收口）
- 优先级：P1
- 状态：**待开工**（拆分自 T29 的剩余项）
- 来源：T29 真机验证中「GUI 提交的作业能否跑完」这一条一直没能闭环

## 为什么单独抽一个任务

端到端验证分两条通道，口径不同、证据形态也不同：

- **CLI 通道（默认，先用它统一）**：`kairos-cli` 直接跑「生成 case → 送进 VM →
  脱离会话求解 → 结果回传 → 结果扫描/读场」，全程可脚本化、可重放、输出可断言。
  求解链路本身、case 契约、结果读取的验证一律先走这条，**除非验证目标本身是界面行为**。
- **GUI 通道（本任务）**：验证桌面端**作业编排**——提交、排队、日志与进度回显、
  取消、结果面板联动，以及虚拟机「作业拉起 / 跑完关闭」的真实行为。这些是适配层
  与前端的行为，CLI 覆盖不到。

## 范围

1. **作业提交与执行**：从求解面板提交 case 目录 → 作业进入「运行中」→ 日志滚动 →
   跑到 endTime → 状态转「已完成」，结果时间目录回传宿主 case 目录。
2. **虚拟机生命周期**：VM 停止时提交作业 → 作业线程自动拉起（日志出现
   「启动虚拟机（作业需要，跑完自动关闭）」）→ 队列空闲后 VM 自动关闭；用户手动启动
   的实例、以及开着 Shell 会话时不被关闭。
3. **失败可见性**：构造一次求解失败（如 `decomposeParDict` 核数与提交核数不符），
   确认作业显示「失败」并给出原因（求解器错误标记优先于退出码），且虚拟机照常收尾。
4. **取消**：运行中取消 → 进程组被杀、状态转「已取消」、虚拟机按空闲规则收尾。
5. **结果面板联动**：作业完成后结果面板能扫描到新时间目录并载入场。

## 验收证据

- 每条给出：操作步骤、界面状态截图或状态文本、宿主 case 目录产物（时间目录清单）、
  `multipass list` 的虚拟机状态前后对照；
- 至少覆盖「VM 从 Stopped 起步」的完整一轮（这是省内存策略的核心路径）；
- 失败与取消各一轮。

## 已知障碍（需要人配合）

本仓库的自动 GUI 操作走辅助功能树（AX）。上一轮尝试时，求解面板的 case 目录输入框
在 AX 树里不可见（面板处于折叠 / 未展开状态），因此**需要有人在界面上把求解面板展开
一次**，之后即可按上面步骤跑。若届时仍拿不到输入通道，退化方案是：用 CLI 跑求解链路、
GUI 侧只做「提交同样 case 目录」这一步的点击验证。

## 不做

- 不重复验证求解器本身（属 T29 与上游用例）；
- 不做视觉像素级比对（属视口截图核验，见 T29 遗留项）。
