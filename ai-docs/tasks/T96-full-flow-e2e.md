# T96 · 全流程集成测试（正常使用路径：几何 → 网格 → case → 求解 → 结果）

- 阶段：E1（求解链路闭环）
- 依赖：T11（填充端到端闭环）、T29（真实求解）、T36（bundle 进 VM 执行）、T85（Linux 原生通道）
- 优先级：P1
- 状态：**第一步已落地**（L1 + L2 两层与编排收口）；GUI 编排层归 T94
- 来源：真机上出现「提交求解作业即失败」而后端单元测试全绿——`case 解压进虚拟机失败：tar: Ignoring unknown extended header keyword 'LIBARCHIVE.xattr.com.apple.provenance'` 与「部署后仍提示未部署」两处缺陷都住在「只有界面走过、没有任何自动化覆盖」的命令层里

## 为什么要单独一层

既有的测试地图是**单元层**（core 纯逻辑 100% 行覆盖 + 适配层少量单测 + DTO 契约），
而用户实际做的事是「导入几何 → 生成网格 → 设置材料工艺 → 提交求解 → 看结果」这条**链**。
链上的接缝——命令怎么拼、分步怎么排、成败怎么判、产物落在哪——此前没有一处自动验证，
踩到的两次都是这个形态：

1. **判定口径**：宿主命令只看退出码（tar 的 pax 扩展头警告不该算失败）。缺这条口径的
   后果是「解压其实成功、作业却被判失败」，而单元测试里没有任何东西会走这条判定。
2. **shell 引号**：`detached_launch_command` 把脚本喂给 `bash -lc` 时少了外层单引号，
   真机表现为 `求解启动失败：bash: -c: line 1: unexpected EOF while looking for matching '`，
   求解**永远不会启动**；而它的单测只断言「字符串包含 `setsid bash -lc`」，把缺陷锁成了"期望"。

两条都不是「算法错」，是「接缝没人跑」。因此本任务的目标不是提高行覆盖率，而是**把用户路径
串起来跑一遍**，并优先断言可观察产物（case 结构、时间目录、读场结果、退出码）。

## 分层

| 层  | 覆盖                                          | 触发条件                                          | 跑法                                                     |
| --- | --------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| L1  | 几何 → 网格 → case → 结果扫描（宿主）         | 无条件（CI 三端都跑）                             | `cargo test -p kairos-tests --test e2e`                  |
| L2  | case 进 VM → 脱离会话求解 → 结果回传 → 读场   | `KAIROS_E2E_VM=1` + multipass / 实例 / 已部署环境 | 同上（带环境变量）；`KAIROS_E2E_KEEP=1` 保留现场用于排查 |
| L3  | 界面提交、队列、日志与进度、取消、VM 自动启停 | 需人展开求解面板一次                              | 见 [T94](T94-gui-e2e-verification.md)                    |

L2 的编排直接调 `kairos_core::services::vm_run`（与桌面端作业线程**同一段代码**），测试只提供
「怎么跑宿主命令」的 runner 与断言——否则又变成「测试自己实现一遍，产品里跑另一遍」，
接缝照样漏。

## 范围

### 已落地（第一步）

1. **编排收口**（可测化前提）：新增 `kairos-core::services::vm_run`——`HostCommand` / `HostRunner`
   抽象 + `stage_case`（打包 → 传输 → VM 内解压）+ `copy_results`（清单 → 打包 → 传输 → 宿主解压）
   - `poll_log_once`（日志与退出码回读）+ `judge`/`failure`（**成败口径的唯一出处**）。
     桌面端 `commands/jobs.rs` 改为调用它，只保留 runner 实现（PATH 修补 + 超时）。
     `solve_script`（source 环境 → 进 case → 分步求解）也从适配层收进 core。
2. **L1 + L2 集成测试**：`tests/rust/e2e/main.rs`（新 `[[test]]` 目标）。
3. **shell 语法契约用例**：`generated_shell_commands_parse_with_bash` 把本模块产出的每条命令
   交给 `bash -n` 解析（含带单引号的路径）——引号失衡这类问题只有交给 shell 才算验证过。
4. **顺带修掉的两个缺陷**（都是 L2 首跑抓出来的）：
   - `detached_launch_command` 缺外层引号（求解无法在 VM 内启动）；
   - 原生求解脚本的 `export PATH='<前缀>:$PATH'` 前缀未转义（应用数据目录含引号时会截断命令）。

### 待做（本任务剩余）

1. **runner 的执行策略也进自动化**：现在「起进程 + 等退出码 + 超时」在适配层（macOS 专属 cfg），
   只被 L2 真机覆盖。计划把「起进程 + 超时 + 判定」抽成可注入的 `ProcessRunner`，core 侧用
   跨平台的最小命令（`sh -c` / `cmd /C`）做用例，真机层只验证通道。
2. **失败路径进 L2**：求解器致命错误（如故意写坏 `decomposeParDict`）→ 作业必须报失败且带原因；
   取消（杀进程组）→ 结果不完整但可读。
3. **发布前门禁**：L2 需要在有人工 VM 的机器上跑，纳入「发版前手动跑一次并记录证据」的清单
   （与 T29 / T48 的真机口径一致），并在 [tests/README.md](../../tests/README.md) 写明跑法与前置。
4. **DOE / 寻优批处理**（T92 / T93）复用同一条 L2 通道：批次里每一次运行都是一次「正常使用」，
   跑通的判据与本测试一致。

## 验收标准

- L1 在 CI 三端（macOS / Windows / Linux）无条件通过；
- L2 在一台装有 multipass + 已部署环境的机器上通过，且**至少覆盖一次真实求解**（退出码 0、
  日志有时间步推进、结果回传后宿主侧能扫描并读出速度场）；
- L2 抓出的缺陷都要有对应回归用例（当前两条已体现在 `vm_run` 用例与 shell 语法契约用例里）；
- 测试断言写在**可观察产物**上，不断言内部调用序列；失败信息必须带出定位线索（日志尾部、
  现场路径），否则排查成本会把这条测试变成负担。

## 已知限制

- L2 依赖真机 VM，**不能**进 CI（托管 runner 没有 multipass 与 120MB 求解环境）；
- L2 的算例刻意取小（样例方盒 10mm + 2mm 网格 ≈ 600 四面体），秒级完成——它验证的是链路
  接缝，不是求解器物理（后者属 T29 与上游用例）；
- 不测 GUI（属 T94），不做像素比对（属视口截图核验）。

## 不做

- 不重复求解器本身的物理验证（T29）；
- 不引入外部的 e2e 框架（仓库既有 `cargo test` + `bun run verify` 两套入口足够）。
