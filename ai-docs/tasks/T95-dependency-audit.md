# T95 · 依赖取向审查：用现成库 vs 自造轮子

- 阶段：E4（工程质量）
- 依赖：无（随时可做，逐条出结论即可开工）
- 优先级：P2
- 状态：**待开工**
- 来源：T60 讨论 PPTX 导出时提出的问题——「有些功能是不是用库更合适，而不是自己写」

## 目标

对全仓库做一次**依赖取向审查**：逐块判断「该用成熟库 / 该继续自己写」，给出结论与理由，
并把结论落成可执行的改动清单（能当场改的当轮改掉，需要取舍的记入本任务的决策表）。

这不是「能引库就引库」的运动：本项目有明确约束（见下），很多看着像轮子的东西其实是
**产品自己的规格**，必须留在仓库里。

## 判断标准（按优先级）

1. **规格归属**：这是「通用问题」还是「本产品的规格」？
   - 通用问题（CSV/压缩/日期/HTTP/UI 工具）→ 优先用库；
   - 本产品规格（OpenFOAM case 文件格式、case 契约、网格拓扑与体素化口径、浇口/流道语义、
     KairosError 契约）→ **必须自己写**，库表达不了我们的契约，套库反而多一层翻译。
2. **许可与合规**：只接受 permissive（MIT / Apache-2.0 / BSD / ISC 等）。GPL/AGPL 一律不得
   进进程内依赖（现有 GPL 隔离靠「子进程 + 文件交换」，见 AGENTS.md）；GPU 相关不得引入
   单厂商 SDK（统一走 wgpu）。
3. **可验证性**：`kairos-core` 有 100% 行覆盖门槛，前端逻辑层四维 100%。引库后**包装层仍要
   被测到**；库若有不可控的网络 / 全局状态 / 平台分支，评估它会不会把覆盖率门禁变成噪声。
4. **体积与离线**：桌面应用、离线可用。前端依赖按 gzip 后体积算账（例如 pptxgenjs ≈1 MB）。
5. **维护度与可替代性**：下载量、最近发版时间、API 稳定度；能否在几百行内自己写清并覆盖测试。
   若自己写的成本 < 引库 + 适配 + 学习 + 升级成本，就自己写。

## 审查面（逐条给结论，不要求全改）

Rust（`src-crates/*`）：

- CSV 解析与导出（材料批量导入 / 结果导出等）；
- STL / STEP / IGES 解析——**注意**：这些是行业格式，属「通用问题」，但解析精度与错误口径
  直接影响网格与求解契约，需单独权衡（现为手写解析器）；
- 几何与网格算法（体素化、自交检测、纵横比、降维中面）——通用几何谓词可考虑 permissive 的
  `nalgebra` / `parry3d` 一类库，但**体素化与网格口径是产品规格**，不外包；
- 归档与压缩：现在复制 case / 回传结果靠调用系统 `tar`（子进程），可评估 `tar` + `flate2` 纯
  Rust 方案（去掉对宿主 tar 的依赖，利于三端一致）；
- 哈希校验（下载完整性）、文本编码 / 路径工具（已有 `services/paths.rs`，与 `std::path` 分工要写明）；
- 时间与随机 id（`new_id` 现为自造）。

TS（`src-web/*`）：

- 通用工具：防抖 / 节流、深拷贝、对象与数组工具、单位与数值格式化、日期；
  （VueUse 类库是否值得整体引入，还是逐个函数自写）
- 数据导入导出：CSV / JSON 的解析与构造；
- 图表与视觉：XY 曲线、色标 / 色映射、画布绘制——现为自绘，需评估「自绘 vs 图表库」在
  体积、交互一致性、与 3D 视口联动的代价；
- 编辑器 / 虚拟滚动 / 剪贴板 / 拖拽等交互设施。

## 产出

1. **决策表**（写在本任务文件里）：位置 / 现状（自写 XX 行）/ 候选库（版本、许可、体积）/
   结论（引库 / 自写 / 保持）/ 理由 / 代价（改动量、覆盖影响）；
2. 能当场改的：拆成小提交直接改（每个提交带消融或对拍证据），并在 timeline 记一行；
3. 需要取舍的（如 STEP 解析、图表库）：先出对比结论，等确认后再动，不擅自替换核心路径。

## 不做

- 不改动「产品规格」类的自写实现（见标准 1）；
- 不为了减少代码行数引入重量级依赖；
- 不动已有且验证过的依赖（tauri / wgpu / serde / vue / pinia 等）。
