# T21 · 里程碑评审与整体优化（循环任务）

- 阶段：M0–M5（**每个里程碑结束时强制执行一轮**，不适用则不得开启下一里程碑）
- 依赖：当前里程碑的全部任务
- 优先级：P0

## 目标

在每个里程碑边界做一次整体性的评审与优化收口：确认该里程碑没有只顾功能、欠下架构 / 性能 / 质量 / 文档的债，并把评审发现转化为明确的处理项。整体优化与 review 是计划的一部分，不是随手的额外动作。

## 评审清单（逐项核对，覆盖本里程碑新增与改动的代码）

1. **架构一致性**：依赖方向无违例（core 无 tauri、commands 薄、组件不直接 invoke）；新 DTO 双端镜像与契约测试齐全；
2. **性能预算对照**：用 T01 基准套件跑当前数字，与本里程碑设定的预算逐条对比，超标项必须给出处理结论（当场优化 / 立优化任务 / 修订预算并说明理由）；
3. **代码与注释质量**：命名一致性、注释与实现相符且解释"为什么"、无 TODO/FIXME 残留、无死代码与投机性 API；
4. **文档同步**：README / ARCHITECTURE / AGENTS 与实际实现一致，路径与数字无漂移；
5. **测试覆盖缺口**：核心逻辑有无未覆盖分支，契约测试是否锁住新形状；
6. **依赖健康**：未使用依赖（knip）、可升级项、许可证合规（特别是 GPU 与求解器集成引入的传递依赖）；
7. **安全**：CSP 现状、capabilities 最小化、依赖漏洞通告；
8. **上轮遗留追踪**：上一轮评审的"接受/缓办"项逐条重新评估。

## 处理规则

评审发现分三类，全部显式记录，不允许"看了但没结论"：

- **立即修**：小而明确的问题（注释漂移、命名不一致、小的性能修正），本轮直接修；
- **回流任务**：需要独立处理的项，新建任务文件并加入索引（编号顺延）；
- **接受并记录**：确认暂不处理的项，写明理由与重评条件，进入下轮评审清单。

## 范围

- 上述清单的全部评审与"立即修"类优化；
- 评审报告 `ai-docs/reviews/M<编号>-review.md`（发现、分类、性能数字、与上轮对照）；
- 优化以独立提交落库（拆分提交，保持一条 commit 一个主题）。

## 非目标

- 下一里程碑的需求变更评审（那是计划修订，另行走 README 的任务修订流程）；
- 为评审而评审的仪式性产出——每条发现必须落到"修 / 回流 / 接受"之一。

## 交付物

- 本轮评审报告（八项清单逐项结论 + 性能数字表）；
- "立即修"类优化的提交；
- 回流任务文件与索引更新；
- timeline 追加一行（评审结论摘要）。

## 验收标准

- 八项清单每项有明确结论与证据（数字 / grep 结果 / 测试输出），无"未检查"项；
- 性能数字与本里程碑预算的对照表完整；
- "立即修"项全部修复且 `bun run verify` 全绿；
- 回流任务均已建档并在索引可见；
- 报告入库，timeline 有对应记录。
