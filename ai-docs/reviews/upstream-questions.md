  也加了回归用例；但我们消费的 bundle 仍是 v0.2.5（含该缺陷）。

## 4. 【已关闭】release 是否提供校验值（SHA256SUMS）

- **现状**：上游 release 只有两个归档（`moldingFoam-v0.2.5-{amd64,arm64}.tar.xz`），
  没有校验文件。我们已做：下载后计算 SHA-256 落进应用清单（`ManifestEntry.sha256`），
  可跨会话核对同一文件是否被替换，供追溯。
- **结论（2026-09-14）**：不需要单独文件了——GitHub 已为每个 release 资产提供 `digest` 字段（`sha256:<hex>`，`gh api …/releases/tags/v1.0.0` 可读，发行页面也显示）。Kairos 侧已接入：下载后计算摘要并与该字段比对，不一致即删文件并报错。核验：本机已装的 v1.0.0 arm64 包`sha256 = ecbd8b09…` 与官方公布值完全一致。
- **影响**：有官方值后，我们能把「记录摘要」升级为「比对校验」，供应链完整性才算闭环。
  在此之前应用侧无法判断下载物是否被中间人替换。

- **我们的现状处置**：作业成败以「求解到 endTime + 输出完整」为准，退出码不单独作为判定依据
  （失败判定优先看求解器错误标记，见 `job_logic::job_failure`）。
- **需要上游**：这是否已知；若不修，是否会随 046 的版本一并变化。
- **影响**：自动化验收与 CI 只能绕过退出码，长期会掩盖真实的进程级问题。

## 7. 模板值：按件选档（上游建议 P1）

上游实测（契约 case + 真实件 cli10，只改 `nSubCycles` / `nCorrectors` 两个旋钮）：

| 选项                                   | 收益                                                     | 代价                                                                        |
| -------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| `nCorrectors` 2 → 1                    | 契约 case 墙钟 −30%；真实件 cli10 −14%（件越大收益越大） | 熔接痕对称性探针 0.554% → 1.226%；实件质量预算残差 −3.76e-05 → +1.42e-04 kg |
| `nSubCycles` 6 → 12 且 `nCorrectors` 1 | 对称性恢复到 0.83%                                       | 真实件比原模板慢 14% → 实件不推荐                                           |
| `MULESCorr yes`                        | —                                                        | dt 塌缩 3×、成本 3× → **禁用**                                              |
| 自适应子循环表（库朗插值）             | 仅 −2%                                                   | 不值得（填充期占 95–99% 步数）                                              |

**我们的动作**：挑 1–2 个件做 `(6,2)` vs `(6,1)` 对照，确认我们的 e2e 判据
（填充 / V-P 切换 / 保压跟随）都过、残差量级可接受后再决定是否改默认。
物理路径是稳的：三档的 V/P 切换都在 fill ≈ 0.960 / t ≈ 1.080 s。

## 8. 体素分辨率与时间步口径（上游建议 P2）

- 质量守恒误差 ∝ dt（一阶，三点定标 0.97–1.06）→ 想留余量就缩 `maxAlphaCo`，成本同比例上升；
- 固定 dt 下误差随网格加密**一阶上升**（细化不改善守恒），而自适应 dt 会更快变小（实测 2× 加密 → dt ÷8）；
- 门禁余量建议 **≥ 3–5× 漂移带**（跨平台差异 1–10%）；
- 结论：**分辨率按几何 / 流动特征定，用 dt 调余量，不要用加密网格买精度**。

**我们的动作**：T57 的网格预估与 T74 的浇口速度阈值都不受影响；这条主要影响我们对
「网格加密后守恒变差」的解释口径，已记入 T29 的验收说明。

## 9. 退出崩溃（037）：上游排查边界与过渡口径

- 只在 **np4**、且求解正常打印 `End` 之后出现（`malloc_consolidate(): unaligned fastbin chunk detected`，
  退出码非零）；串行与秒级小 case 干净；
- bundle 无重复载入（`libmoldingFoam*.so` 单一 inode）、该 VM 无 apt 树可混用；用当前源码重建的库
  在同一 VM 上同样崩 → 与求解器源码无关，属 **bundle / VM 环境相关**；
- 上游建议的两个对照：① `mpirun --mca btl self,tcp`（排除 OpenMPI vader/CMA 共享内存路径）；
  ② 崩溃时 `MALLOC_CHECK_=3` + gdb 取栈；
- **过渡期兜底**：run 脚本按「日志含 `End` 且无 `FATAL`」判成功、忽略退出码。

**我们的状态**：Kairos 的失败判定本来就以求解器错误标记优先、退出码次之（`job_logic::job_failure`），
与这条兜底口径一致；不需改动。等上游给出两个对照的结论后再决定是否收紧。
