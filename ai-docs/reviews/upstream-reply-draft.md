## 1. 037（退出崩溃）的结论链不成立

**你的说法**：用当前源码重建的库在同一 VM 上同样崩 → 「与求解器源码无关，属 bundle / VM 环境相关」。

**为什么推不出这个结论**：重建后仍崩，只排除了「bundle 打包 / 编译器差异」，**没有排除源码本身**——
同一份源码换工具链重建都崩，恰恰说明崩溃路径在这份代码里，只是不依赖构建方式。

**我的反例**：v1.0.0 + np4 + 5000 四面体 case（CLI 生成，`--cores 4`），
1389 步跑到 `End`、**退出码 0**，未复现。也就是说「只在 np4、End 之后出现」至少在小件上不成立。

**需要你**：

1. 给出复现条件（件规模 / 具体 case / 内存与 OpenMPI 版本），否则我们无法在自己的验收里
   区分「环境问题」与「并行析构 bug」；
2. 按你自己提的方案取**栈**：`MALLOC_CHECK_=3` + gdb（`mpirun --mca btl self,tcp` 只排除
   vader/CMA 通道，不能替代栈证据）；
3. 明确一件事：崩溃发生在 `End` 之后时，**输出文件是否完整**？这决定我们能否在验收里忽略退出码
   （我们现在是「日志含 End 且无 FATAL 即成功」，但需要你确认这个判据不会掩盖真实的数据缺失）。

## 2. dt 定标的指数与量纲不符

**你的说法**：固定 dt 下质量守恒误差随网格加密一阶上升；自适应 dt「2× 加密 → dt ÷8」；
门禁余量建议 ≥ 3–5×。

**问题**：2× 细化对应 dt ÷8 意味着 dt ∝ Δx³，与常见的 Δx（对流 Courant）或 Δx²（扩散）都对不上。
若这是 `maxAlphaCo` 自适应与界面分辨率共同作用的结果，需要你说明 **dt 的定义**（是 maxAlphaCo 下的
最大稳定步长，还是实际平均步长）与推导。

**为什么较真**：我们要用这个定标关系来定门禁余量。指数不确定，余量建议就没有可换算的依据
（我们现在的做法是「按几何/流动特征定分辨率、用 dt 调余量」，需要这个关系才能落成数值门槛）。

## 4. MULESCorr 的「禁用」结论范围不明

**你的说法**：`MULESCorr yes` → dt 塌缩 3×、成本 3× → 禁用。

**问题**：MULESCorr 改变的是 alpha 通量的修正方式，属**求解行为**而非「模板值」。需要明确这是
在你特定 case / 时间格式（Euler？backward？）与 `maxAlphaCo 0.1` 下的实测，还是通用建议。
否则照做会改动物理行为，超出「调模板参数」的范畴，我们要单独评估。
